# 制作与验证细节

在编写提取/暗底提示词、定义纹理契约或复核本流程来源时读取。示例应按实际对象修改，不把商业体坐标或历史参数写成通用算法。

## 局部提取提示词示例

> 仅提取所连局部参考中的【对象】。它是唯一主体，保留原观察方向、俯角、屋顶边线斜率、可见立面比例、轮廓和材质。只去除无关背景，对必要遮挡做最少补全，不重新设计，不转成等距投影，不增加对象。完整主体占画布主要区域，少量透明留边，底座不截断。真正透明 PNG，原生 2K。

提示词不能代替输入裁切。先查看输入中主体是否足够大；不要靠追加大量相机描述补救整景输入。

远景示例：

> 整条远景建筑带作为一个透明层，保持楼房间相对位置、大小、间距和细长轮廓；去除天空、山体和前景公路，保留建筑之间需要的树带，不拆单楼、不重新排列城市。

特别细长的参考若被平台拒绝，可在不拉伸内容的情况下加输入留白，并记录偏移；不裁掉整群，也不把增加的留白当作对象内容。

## 干净暗底提示词示例

> 对所连独立建筑仅修改照明：关闭每扇窗、玻璃门和全部屏面，清除烘焙在墙面上的暖光、紫蓝光晕、反光和照亮痕迹。保留深蓝灰环境照明、材质纹理和各立面明暗。关灯屏面是带微弱天空反射的深蓝玻璃，不是死黑矩形；窗框保持正常材质，不描黑边、不涂黑。楼体轮廓、透视、屋顶线、每个窗口和屏幕的位置、画布构图保持不变，不新增窗户或景物。独立完整对象，透明 PNG，原生 2K。

有原始暗景参考时，连接同一对象的紧裁切暗图，仅指导材质与环境色；以独立资产为几何基准。模型输出仍需配准与人工查看，不能仅凭提示词宣称结构一致。

全部窗户亮灯的补充：

> 点亮所有现有可见窗户、玻璃门和底层玻璃带，包括需保留的阁楼窗口；窗内可有自然层次，但每个窗组都明确亮着。窗框和分隔条保持清晰，不增加窗户。

## 建议的资产契约

按当前任务选用名称和格式，不要求机械创建全部文件：

```text
base-unlit.png        固定关灯材质与权威 alpha
windows-light.png     窗灯的发光、受光及必要光晕增量
screens-light.png     屏幕的独立光增量
*-mask.png            对应发光区域，便于编辑与验证
manifest.json         尺寸、编码、混合、配准和来源信息
scene-layout.json     alpha 范围、锚点、位置、缩放、层次及遮挡
preview.html          可操作预览
validation.json       实际执行的检查与限制
```

需要单独控制墙面受光或光晕时，另存接收面与外溢图层。任何通道都不能悄悄改变底图 alpha 或裁切范围。

manifest 至少能回答：

- 哪张是暗底，是否由模型去除烘焙光照，而非亮图扣黑？
- 尺寸是否为实际生成的 2K？输入裁切原生尺寸是多少？
- 哪个 alpha/锚点为权威？做过哪些配准、边缘延展和人工遮罩？
- 灯光纹理存线性值还是 sRGB 编码值？采用加法还是普通透明覆盖？
- 哪些光受同一滑块控制，哪些是独立通道？

## 线性光照合成

对于归一化 sRGB 通道 `s`：

```text
decode(s) = s / 12.92                         if s <= 0.04045
            ((s + 0.055) / 1.055) ^ 2.4       otherwise

encode(l) = 12.92 * l                         if l <= 0.0031308
            1.055 * l ^ (1 / 2.4) - 0.055    otherwise
```

固定暗底 `B`，窗灯增量 `Lw`，屏幕增量 `Ls`：

```text
Clinear = decode(B) + windowGain * Lw + screenGain * Ls
Cdisplay = encode(Clinear)
```

若光增量纹理为了 PNG 交付而存成 `encode(Lw)`，着色器采样后要解码。接收面和光晕可以归入各自增量，保持通道独立。超过显示范围的光需要明确采用裁切或映射；高强度视觉演示不等于真实光照标定。

玻璃/屏面配准后，可以在其发光区域取 `max(decode(lit) - decode(B), 0)`；不把楼体纹理和模型边界的差异提取成灯光。接收面另用该光源的平滑场、墙面/地面范围及遮挡生成。不要以颜色阈值遗漏中性高光或紫色屏幕区域。

预合成两张不透明整景图时，可先完整绘制暗景，再按强度覆盖亮景，或在线性空间插值；不要让两张图都带互补透明度后普通覆盖，造成中间档位透明、额外变暗。

## 验证中的有效证据

- 取窗玻璃内部与屏幕内部各一个像素：窗灯打开只让前者明显变化；屏幕打开只让后者明显变化。避开受光交叠区，另检有意的共同接收面。
- 两通道归零，改变窗光冷暖，比较渲染结果是否完全相同。这能发现调色误作用于底材。
- 关灯、单开各通道、全亮以及中间和较高强度截图；不仅比较截图是否不同，还查看遮罩是否跨框、出现残余光晕或新增暗边。
- 静止前后查看绘制计数，验证无新增持续循环；报告实际纹理数与解码体积。事件耗时、短时截图或无 WebGL 错误不等于真实设备性能通过。
- 离线 HTML 若使用 WebGL，注意本地图片的安全源限制。可将预览纹理内嵌为 data URL，或用本地服务；不要为演示引入运行时 CDN。

## 可移植校验清单

`scripts/validate_bundle.py` 使用 Python 与 Pillow，读取显式资源表，不猜测历史目录布局。示例：

```json
{
  "version": 1,
  "resources": [
    {"id":"base", "path":"assets/base.png", "role":"base", "width":2736, "height":1536, "canvasGroup":"building", "requireTransparency":true},
    {"id":"window-light", "path":"assets/window-light.png", "role":"light", "width":2736, "height":1536, "canvasGroup":"building"}
  ],
  "channels": [
    {"id":"windows", "emission":["window-light"], "receivers":[], "halo":[]}
  ]
}
```

资源路径须在包内；可选 `sha256` 验证字节。每张生产图片至少四百万像素，组内画布相同；有透明要求的底图须有实际透明像素。预览截图不列为生产资源。每个光增量资源只归一个独立通道；共享配光参数/源素材不必复制为多个光增量。报告说明的能力边界仍需人工及浏览器验收。
