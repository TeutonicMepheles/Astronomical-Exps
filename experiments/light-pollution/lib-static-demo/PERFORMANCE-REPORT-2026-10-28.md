# 光污染候选场景性能分析与优化报告

日期：2026-10-28。对象：`lib-static-demo/standalone.html`，以及生成它的同目录源码。当前分支 `experiment/light-pollution/sky-preview`，起始 HEAD 为 `d357477`，相对远程 ahead 1。起始工作区已有大量未提交实现；本次保留并基于这些实现优化，没有提交、推送或覆盖已有草稿。

## 结论

已复现间歇性主线程停顿，并完成第一轮不降低画质的优化。主要问题是**动态画面重复生成、无变化 DOM 更新和导航事件连锁执行**，不是简单的星点数量过多。优化后的同条件短时测量未再出现 50ms 以上长任务。此结论只覆盖本机默认候选场景；不能声称所有设备、所有导入资源、用户已有浏览器草稿或长时间运行均已达标。

指定文件是候选场景与编辑器，不是根实验 `experiments/light-pollution/index.html`。本次优化已重新构建指定 standalone；没有把候选实现合并进正式入口。根浏览器回归覆盖正式入口，但正式入口没有进行同样的性能定量审计。

## 渲染路径与问题分析

### 1. 广告屏重复生成和上传（已优化）

`app.js` 的 compose 先建立水面发光源缓冲，再绘制实际建筑。两条路径都调用广告屏 render。旧 `objects.js` 对正常动画中的亮广告屏无条件重新执行 texture、透视 warp、纹理上传和 Canvas 拷贝；同一个动画时间片被重复计算。

现在缓存结果关联 `frameTime`，同一动画时间片的倒影与主画面复用透视结果。现有参数、图片、角点、视频切换和撤销逻辑仍通过清空缓存失效；下一时间片自动重新生成。没有关闭广告、Bloom、转场或水面倒影。

### 2. 每帧导航事件和布局读写（已优化）

旧 paint 每次更新天空 transform、标签 textContent、dataset，再调用 navigation.sync；后者即使位置不变也派发 streetnavigationchange，引发提示层同步。提示同步包含布局尺寸读取、对象快照和遮挡状态判断，随后 paint 又主动调用一次提示同步。

现在 paint 仅在视图、模式、编辑状态改变时更新视图 DOM 与导航；导航自身也按编辑状态、位置比例、可移动宽度去重。ResizeObserver、拖动、按钮和位置滑条仍能更新导航。场景 Canvas 和选中框继续正常绘制。

### 3. WebGL 目标尺寸无条件重置（已优化）

旧 warp 每次写 projector.width/height，哪怕尺寸不变也重置绘制缓冲。现在尺寸实际变化时才赋值，保持原分辨率、透视算法与 CPU fallback。

### 4. 灯光面板重复写入（已优化）

旧 light-environment.update 每次合成都重写指数、贡献文本和按钮状态。现在以 enabled、amount、contributions 为签名跳过无变化的 UI 写入；内部报告仍刷新，避免导出几何或光源状态过期。

### 5. 多个动画循环触发全场景重绘（尚待结构优化）

水面与 objects 各有约 50ms 的节流动画循环，均可触发完整 compose；天空组件另行渲染。即使只改变水流，也会重画建筑、灯具、倒影与提示层。50ms 节流还受实际刷新周期量化，不能等同于精确 20fps。第一轮没有改动时间模型，以控制回归风险。

建议统一单个调度入口：收集水流、广告、窗帘的时间状态与 dirty 标记，每个浏览器帧最多合成一次。用户交互优先于装饰动画；隐藏页暂停，恢复页限制 elapsed，避免视频或动画突然跳跃。必须覆盖暂停广告但刷新带继续、零水速、减少动态效果、隐藏图层与后台恢复等既有语义。

### 6. 大面积 CPU/GPU 往返及静态内容重画（尚待优化）

主逻辑画布 2172×724，单个 RGBA 缓冲约 6.0MiB。反射源先由 Canvas 2D 合成，再缩到 1086×362，最后上传 WebGL；其像素载荷每次约 1.5MiB，不包括转换和同步成本。运行路径还存在 WebGL→2D 复制、blur 滤镜、静态建筑反复 drawImage，以及 getData 深拷贝。

建议分别缓存静态发光源和动态广告倒影；按光源版本更新纹理。静态图层只能按编辑后的实际排序分段缓存，不能假设水面永远在最上层。后续可让水面和投影共用 GPU 管线，减少读回；这属于较大改造，需保持 Alpha、色温、遮挡、导入图和失去 WebGL 上下文后的行为。

### 7. 初始化、资源与内存（尚待优化）

standalone 约 32.55MB（31.04MiB），包含新旧素材与动画图集。浏览器需要解析内嵌数据并解码，当前 ready 约 2.1 秒。候选图的去白底、像素遍历、遮罩和窗口归属计算也发生在初始化或缓存失效时。

建议在导出阶段预计算默认素材的 Alpha、默认窗口纹理和遮罩；保留运行时处理导入图片的路径。新旧场景可提供独立离线导出，减少不使用资源；不要悄悄移除现有 legacy 入口。长时间内存需用独立测试观察趋势，当前单点 heap 无法证明不存在泄漏，也不能声称总内存仅 86.4MB。

## 后续优化优先级与验收方案

| 优先级 | 工作 | 预期收益 | 验证重点 |
| --- | --- | --- | --- |
| P0 已完成 | 广告帧复用、DOM/导航去重、尺寸去重 | 减少冗余上传及布局工作 | 本报告已有测量与回归 |
| P1 | 单调度器、一次合成、隐藏页停工 | 减少全场景重绘与后台消耗 | 时间连续、输入响应、暂停/恢复 |
| P1 | 提示层按几何/状态/尺寸失效；避免深拷贝图片字符串 | 降低剩余 sync 和 GC 开销 | 提示完成状态、遮挡、选中/悬停一致 |
| P1 | 静态反射与静态图层缓存 | 降低填充、blur、纹理上传 | 任意排序、透明度、关灯、换图、撤销 |
| P2 | 默认资源离线预处理、按场景导出 | 降低冷启动、解析和解码成本 | file:// 完全离线、旧场景可用 |
| P2 | 共用 GPU 管线与可选质量档 | 为低配白板留余量 | 画质对照、失去上下文、GPU 不可用 |

这些收益是工程预期，不是已测量的承诺。质量档会影响观感，应先在目标设备确认画质取舍；不擅自把降分辨率或关闭效果作为默认方案。项目尚无正式性能阈值，本报告不替项目设定 60fps 或内存上限。

完整设备验收应包括：用户实际 Chrome 的现有草稿、干净默认场景、1080p/4K 与目标 DPR、目标白板 GPU/触控；默认播放、两个广告片段跨转场、全窗帘摆动、水面全亮、多次亮度/色温拖动、缩放和平移、拖角点、遮罩导入、撤销重做、恢复草稿、后台再前台。每项至少重复三次，另做长时间播放和多次换图的内存趋势测试。记录 rAF 尾部、长任务、交互延迟、实际内容更新率和 GPU/进程内存；不要只看平均 FPS。
