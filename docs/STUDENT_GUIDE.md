# 贡献者使用说明

你负责制作一个完整的天文实验网页。平时在自己的分支开发和备份，整页完成后交给维护者审核。下面的操作可以让 Agent（如 Codex）协助完成。

## 第一次开始

1. 向维护者确认负责的实验，并取得 GitHub 私有仓库访问权限。
2. 安装 Git、Python 3.10+、Node.js 22+、GitHub CLI 和 Agent 工具。可让 Agent 检查是否安装齐全。
3. 把仓库克隆到电脑。克隆会同时下载文件和版本记录，后续才能同步；不要用“下载 ZIP”代替。可对 Agent 说：“请把维护者提供的仓库克隆到一个新文件夹。”
4. 在 Agent 中打开该文件夹，然后说：

> 请使用 astronomical-collab Skill，检查环境并开始我负责的光污染网页。

把“光污染”换成你的实验名称。Skill 是项目为 Agent 准备的操作说明，文件在 [.agents/skills/astronomical-collab/SKILL.md](../.agents/skills/astronomical-collab/SKILL.md)。找不到时，让 Agent 直接读取该文件，无需另行全局安装。

Agent 会检查账号、安装依赖并准备分支。需要登录 GitHub 时，在官方页面操作，不把密码或令牌发到聊天中。无需预先登记用户名；维护者会在交付时核对负责人。

目前工具已接入光污染和牛顿望远镜。其余六页只有需求文档，开始制作前需请维护者补充启动、导出和检查入口。一人负责两页时，建议用两个项目文件夹分别开发。

## 常用操作

| 要做的事 | 对 Agent 说 |
| --- | --- |
| 继续开发 | “继续开发我的光污染网页。” |
| 留下可回退的版本 | “保存进度。” |
| 收工上传备份 | “备份今天的进度。” |
| 收到公共更新通知 | “同步项目公共更新。” |
| 准备交付 | “检查整个网页，导出离线文件，并打开试玩入口。” |
| 试玩通过 | “整页试玩和离线打开都通过，提交验收。” |
| 按审核意见修改 | “按这个 PR 的意见修改：<PR 链接>。” |
| 返修后交付 | “返修已试玩通过，更新这个 PR。” |

## 几个词的意思

| 名称 | 含义 |
| --- | --- |
| 仓库 | 项目文件和版本记录的集合 |
| 分支（branch） | 自己的开发版本，审核前不影响大家共用的版本 |
| 主分支（main） | 维护者审核合并后的公共版本 |
| 提交（commit） | 在电脑上保存一个可追溯的版本 |
| 推送（push） | 把已保存的版本上传到 GitHub |
| PR（Pull Request） | 请维护者审核并合并自己改动的申请 |

编辑器里的“保存文件”不会自动创建版本，也不会上传。建议完成一步就保存版本，每天收工备份；不用等整页完成才上传。

## 怎么检查和交付

先让 Agent 运行自动检查，再亲自从头到尾操作网页：按钮、拖动、前进、返回、重置都要试。随后打开导出的离线文件再检查。科学含义或参数不确定时问维护者。

源码页面要通过本地服务打开，不能直接双击源码 `index.html` 代替。Agent 应提供可点击的本地地址；离线文件另在 `dist/<实验目录>/index.html`。

PR 由 Agent 按模板填写，你只需核对：

- 交付信息：哪个网页、谁负责、从哪里打开。
- 完成内容：已经做了什么。
- 已知问题：还有什么问题；不清楚就写“待检查”。

自动测试通过不等于试玩通过。确认当前版本没问题后再说“提交验收”。如果之后的修改影响操作，需要重新试玩。维护者要求返修时更新原 PR，不另建一份。

## 遇到问题

| 情况 | 处理方式 |
| --- | --- |
| 无法访问仓库 | 检查 GitHub 登录和访问权限，联系维护者。 |
| 提示分支不匹配 | 告诉 Agent 正在做哪个网页，不要强行切换或删除文件。 |
| 提示改了范围外文件 | 让 Agent 列出文件，请维护者判断。 |
| 提示冲突或推送被拒绝 | 让 Agent 保留当前工作并说明原因，不强制推送。 |
| 网络或登录失败 | 先保存本地版本，联网后再备份。 |
| 检查失败 | 让 Agent 查明原因，修复后重试。 |

只修改自己的实验目录。公共组件、其他贡献者网页或项目配置需要改动时，请维护者处理。维护者合并后，下次改进让 Agent 从最新主分支新建任务分支，旧远程分支由维护者处理。
